# Autenticación persistente de Cashier

Branch: `feature/stamps-wallet-prototype`. Implementación local, sin commit, push, merge ni deploy. Los cambios anteriores de Stamps/QA permanecen en el working tree; este reporte describe solamente esta fase de autenticación.

1. **Comportamiento anterior.** Recordarme conservaba tenant y username en Preferences. La sesión con bearer se guardaba en SecureStorage, pero al expirar se descartaba: no había refresh. Eso obligaba a volver a escribir credenciales aunque Recordarme estuviera marcado.

2. **Duración anterior.** El bearer ya duraba 60 minutos (`CashierAuth:AccessTokenMinutes`); el servidor admite 30 segundos de tolerancia de reloj.

3. **Access actual.** Sigue durando 60 minutos, con el formato HMAC v1 existente. Cada emisión incluye un identificador aleatorio para distinguir renovaciones realizadas en el mismo segundo. El campo es opcional al deserializar tokens anteriores. No se cambia la autenticación web.

4. **Refresh.** `CashierAuth:RememberMeRefreshTokenDays=90`. Sólo login con RememberMe=true lo emite. Cada renovación válida abre una ventana nueva de 90 días desde ese momento; uso regular permite continuar durante meses/años. No hay un límite absoluto adicional en esta fase.

5. **Entidad y migration.** `CashierRefreshToken`: Id, TenantId, TenantAdminUserId, TokenHash, CreatedAtUtc, ExpiresAtUtc, RevokedAtUtc. Migration separada `20261004022555_AddCashierRefreshTokens`. Sólo crea esa tabla, su índice único de hash, índice tenant/usuario y la clave alternativa TenantAdminUsers(TenantId,Id) necesaria para una FK compuesta que impide asociar un usuario a otro tenant. Delete Restrict. No campos de replacement ni scheduler.

6. **Almacenamiento servidor.** Se generan 32 bytes criptográficos (256 bits), codificados base64url. La DB conserva exclusivamente SHA-256 hexadecimal de 64 caracteres, nunca el token original. El secreto se entrega únicamente al cliente. Fechas UTC; filtro de tenant en EF. El lookup por hash ignora ese filtro exclusivamente para resolver el tenant del token; luego se establece el scope y se valida usuario/tenant.

7. **Rotación.** POST `/api/auth/cashier/refresh` comprueba vigencia/no revocación, tenant activo, usuario activo, rol permitido y subscription operacional con las reglas existentes. Construye claims con el estado actual. Una única transacción SaveChanges revoca el token anterior e inserta su sucesor. Replay del token anterior se rechaza; no revoca el sucesor legítimo. POST `/api/auth/cashier/login` recibe RememberMe opcional=false, compatible con clientes anteriores. No se registran tokens ni contraseñas en logs.

8. **Concurrencia.** MAUI serializa restore, login, refresh y logout con SemaphoreSlim. Peticiones que rechazaron el mismo access reutilizan el resultado de la primera renovación. RevokedAtUtc es un token de concurrencia EF: dos contextos SQL que rotan el mismo refresh producen un único ganador, y la transacción perdedora no deja un sucesor adicional. Cada login/dispositivo tiene su propia fila. La prueba con SQL Server LocalDB aplica las migrations y verifica este comportamiento. No hay tolerancia que permita replay indefinido.

9. **Startup.** Access vigente restaura directamente; access vencido con refresh intenta renovación y guarda los tokens nuevos. Invalidación definitiva limpia sesión y muestra login. Red/timeout/5xx conserva los datos y muestra restauración con Reintentar, evitando el flash Login → Operaciones. Sesiones antiguas sin refresh requieren un login cuando vence su access. Recordarme=false mantiene solamente memoria, elimina persistencia anterior y no sobrevive al cierre del proceso.

10. **Línea de tiempo.** Después de 1 hora, la siguiente petición/restore renueva automáticamente si se recordó la sesión. Después de 1 día o 20 días, al abrir se renueva y se extiende a otros 90 días. Después de 90+ días sin ninguna renovación, se solicita login. La renovación ocurre al necesitar un access válido; no hay tarea periódica. Un access todavía vigente se usa normalmente hasta su vencimiento.

11. **Logout.** Borra primero SecureStorage/Current y actualiza la UI; intenta revocar el refresh activo en servidor con timeout de 5 segundos. Si está offline, el logout local sigue siendo definitivo y restart no restaura. El token remoto puede permanecer válido hasta caducar si no se pudo contactar al servidor. Un access ya emitido conserva su duración corta. `RevokeAllForUserAsync` queda disponible en scope de tenant para una futura operación de cambio/reset de password; no se implementa Forgot Password.

12. **SecureStorage exacto.** JSON bajo `loyaltycloud.cashier.session.v1`: AccessToken, TokenType, ExpiresAtUtc, TenantSlug, UserId, Username, Role, ProgramType, RefreshToken, RefreshTokenExpiresAtUtc, SessionId. SessionId distingue un nuevo login de una renovación y conserva paneles/operaciones pendientes durante ésta. Preferences sólo guarda tenant y username cuando se marca Recordarme; nunca tokens.

13. **Password.** NO se guarda en DB como credencial nueva, Preferences, SecureStorage ni sesión serializada. Se usa únicamente para el POST de login y se limpia el campo tras login/logout. El hashing de password existente del usuario sigue intacto. Tests inspeccionan el JSON persistido; la implementación existente de Preferences conserva exclusivamente identificadores.

14. **Web y operaciones.** Cookies de Admin/Web Cashier y HMAC Admin API permanecen separados. No cambia MainLayout ni permisos. La renovación MAUI mantiene una identidad estable mientras cambian tokens. Gift Cards y coordinadores de canje comparan esa identidad en vez de igualdad completa del bearer. HTTP repite como máximo una vez tras 401 con el mismo método, payload y clave de idempotencia. El pipeline rechaza auth antes de ejecutar el controlador; no se reintentan errores de red/5xx ni respuestas económicas. Pending/idempotencia y reglas de Stamps/Gift Cards no se modifican en esta fase.
